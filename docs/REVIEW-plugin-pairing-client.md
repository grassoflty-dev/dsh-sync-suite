# Review — mod-plugin-pairing-client

## Verdict
PASS — The client wiring satisfies every hard prohibition (no mount-time clipboard, no seed path in the lean group, no dead-transport hiding, no false announce marker, no automatic `pairingShow`, no dist drift) and all gates are green; two Minor issues remain (a sticky status flag can mask the stopped state, and the recorded byte/test-count claims are stale). Major findings remaining: 0

## Findings

### Blocker
None.

### Major
None. Specifically, none of the explicit fail conditions fired: clipboard is untouched on mount, the lean QR cannot come from a seed, unavailable transports are rendered disabled rather than absent, the marker never claims an unproven announced port, `pairingShow` has exactly one explicit client call site, and dist matches fresh generation.

### Minor
1. **Stopped state can be masked by the sticky rotation notice.** `src/client.js:4545-4548` orders `statusLine` as `failure → rotated → running === false`. `rotated` is set to `true` in `doGenerate` (`src/client.js:4502`) and never reset. After a rotate followed by 停止接受连接, `running === false` is set (`:4526`) and the stop button disables (`:4633`), but the status text still reads 「已重新生成…」 (`:4547`, locale `:377`) instead of 「已停止接受连接」 (`:4548`, locale `:383`). W6 (`test/pairing-client-wiring.test.mjs:319-324`) passes only because it clicks stop on a fresh mount. The kill switch itself genuinely calls `remoteStop` and reflects a stopped control state; only the textual status is ambiguous.
2. **Reported anchors/counts in the brief and docs are stale (favourable drift).** The brief cites `dist/client.js` = 195,196 B both sides, targeted 92/92 and full 667/666/0/1. At review time (tree stable since 18:22) `src/client.js` and `dist/client.js` are both 196,375 B and byte-identical to a fresh `renderClientSource()`; targeted = 95/95 and full = 670/669/0/1. The +3 is the late W14–W16 transport-honesty additions (`test/pairing-client-wiring.test.mjs:481-518`). `docs/PAIRING-CLIENT-TODO.md:14` and `docs/MODULES.md` still quote 190,586 B for `src/client.js`. No assertion was removed or weakened to cause this.

### Nit
1. The kill switch is one-way **from the lean panel**: `remoteStart` exists in the engine (`src/rpc.ts:680-683`, dispatch `:1123-1124`) but the only client call site is the dormant `RemotePanel` (`src/client.js:3598`), not `LeanRemoteGroup` (`:4370-4651`). A stop can be undone via the `remoteStart` RPC / a settings save with `enabled`, but there is no restart button in the lean UI.
2. `lean.remote.mode.unselected` (locale `zh.json:300`) is no longer rendered; the no-network case now uses `lean.remote.transport.none` (`src/client.js:4605`, `:4551`). This diverges from `docs/PAIRING-CLIENT-TODO.md:49-50` but is a more accurate message, not a regression.

## Residual risk & unverified
- **On-device / GUI unverified.** No device commands, no reload, no browser automation were used, per scope. Whether a tablet can actually scan the QR and establish a session remains `unverified`; the review only proves the wiring and payload provenance.
- **Announce hook not wired in production.** With no `onRepublish`, the marker is deliberately always "pending" and republish is requested on every open. The actual announcement re-publish consumer is still a seam (`docs/PAIRING-CLIENT-TODO.md` §5), so "auto-configured" is true for port/token/cert/QR, not for signed announcement updates.
- **Transport honesty copy is not a channel-security proof.** W14–W16 only pin the wording (Tailscale "encrypted", LAN/IPv6 "plain HTTP") and the absence of MITM promises; no TLS listener implementation was audited in this review.
- **Moving tree caveat.** The last in-scope edit observed was at 18:22 (transport-honesty lines + W14–W16 + dist rebuild); all figures above were re-run against that stable snapshot at 18:23–18:27. Any later edit requires re-running checks 9 and 10.
- **Status flag bug (Minor 1)** is source-proven but untested in the rotate→stop sequence; it does not affect the RPC kill switch.
