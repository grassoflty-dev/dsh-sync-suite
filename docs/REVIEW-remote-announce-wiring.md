## Verdict

CONDITIONAL PASS — the page→service→store chain is real, fail-closed, versioned, and the abc evidence reproduces byte-for-byte, but no code in the shipped tree ever provisions a TOFU pin and `firstPairing` is hard-coded false, so `state='refreshed'` is unreachable on device and the action can only ever tell the user 「公告不可信，请手动确认」; accept as a wiring/fail-closed milestone conditional on Q1 key provisioning. **Major findings remaining: 1**

## Findings

### Blocker

None. No refusal path updates `url`/`updatedAt` (`apps/arkui-schedule/entry/src/main/ets/services/remoteAnnounceRefresh.ets:92-111` gates both writes on `outcome.state === 'refreshed'`), and the abc name-level hits reproduce from the HAP itself.

### Major

[M1] `apps/arkui-schedule/entry/src/main/ets/services/remoteAnnounceRefresh.ets:75-80` — `publicKey` and `pinnedKey` are both taken from `remoteAnnounceStore.getPin()`, `firstPairing` is hard-coded `false`, and a repo-wide search finds **no caller of `setPin()`** (`apps/arkui-schedule/entry/src/main/ets/services/remoteAnnounceStore.ets:296-303`); consequently `createEd25519Verifier()` always receives an empty `publicKey`, `hexToBytes()` returns 0 bytes, the 32-byte guard fails (`remoteAnnounceStore.ets:424-428`), and every announcement is refused as `E_ANNOUNCE_SIGNATURE` (or `E_ANNOUNCE_PIN_REQUIRED`). `docs/REMOTE-DISCOVERY.md:24` confirms this is deferred Q1, not a regression, but the practical effect is that the shipped 「按公告刷新地址」 action can only produce a refusal. Required fix: land Q1 key provisioning (a real raw Ed25519 public-key source, distinct from the fingerprint, written through an explicit user-confirmed path), or gate the button with an explicit "no pin configured" state; add an end-to-end positive test with a genuine key/signature before claiming device-level success.

### Minor

[m1] `apps/arkui-schedule/entry/src/main/ets/pages/panes/InstancesPane.ets:181-182` + `apps/arkui-schedule/entry/src/main/ets/pages/panes/InstancesPane.ets:494-523` — on `refreshed`, `announceNotice` is set to the success wording `地址已按公告更新` but is rendered in the danger-coloured / `warning_soft` notice row together with a 「手动确认」 action; with `announceNoticeId=''` the follow-up is a no-op in configurable mode and navigates away to settings on the home pane. Required fix: render the notice row only for `untrusted` / `no-announcement` / `not-newer`, and clear `announceNotice` on success.

[m2] `apps/arkui-schedule/entry/src/main/ets/pages/panes/InstancesPane.ets:99-102` + `apps/arkui-schedule/entry/src/main/ets/pages/panes/InstancesPane.ets:181-183` — `announceNotice` is sticky: `reload()` (`InstancesPane.ets:150-155`) does not clear it, so a refusal for a deleted or edited instance keeps showing until the next refresh. Required fix: clear both notice fields in `reload()` / `aboutToAppear()` or key them to the current `views` set.

[m3] `apps/arkui-schedule/entry/src/main/ets/services/remoteAnnounceStore.ets:383-385` + `apps/arkui-schedule/entry/src/main/ets/model/remoteAnnounce.ts:132` — contract wording conflict: the store defines the pinned value as a raw 64-hex Ed25519 public key while the model calls the field `publicKeyFingerprint` and states the announcement carries only a fingerprint, not raw key material; the service feeds one into the other's slot. The scheme is self-consistent as TOFU-on-raw-key (and fail-closed otherwise), but a host emitting a genuine hash fingerprint can never satisfy `verifyFingerprint()`/`convertKeySync()`. Required fix: decide and document one meaning (pin = raw key, or pin = fingerprint plus a separate key source) and align the field name/comment and the host-side publisher in the same change.

### Nit

[n1] `apps/arkui-schedule/tools/test/remoteAnnounceWiring.test.mjs:212-287` — W3's 12 refusal cases carry no in-describe would-be-accepting control; the positive control lives in W2 (`remoteAnnounceWiring.test.mjs:178-187`), so the suite as executed is not vacuous, but running W3 alone would not prove that a valid announcement is accepted. Required fix: add one "same fixture, valid verifier ⇒ `refreshed`" control inside W3.

## Residual risk & unverified

- **No device run.** ArkTS/SDK behaviour (`createAsyKeyGenerator`, `verifySync(null, {...})`, `PersistentStorage.persistProp` for the new applied key) is only evidenced by a successful `CompileArkTS`; no real DevEco install or on-device verification was performed.
- **M1 blocks any real success.** With no `setPin()` caller and `firstPairing: false`, all on-device refreshes are refusals; the abc proves presence of the code, not a working positive path.
- **Two-store non-atomicity.** `instanceStore.upsert()` and `remoteAnnounceStore.applyUpdatedAt()` are separate commits (`remoteAnnounceRefresh.ets:109-110`); if the latter is lost, the same verified announcement can be re-applied (idempotent, not a swap). Both stores swallow their own write errors, so the outer catch at `:113-123` is unlikely to report `untrusted` after a successful write.
- **Source-shape limits.** W1's regex assertions (test `:106-175`) prove textual wiring only; a runtime import-cycle or platform API mismatch would not be caught by Node tests.
- **Provenance.** `remoteAnnounceStore.ets` is untracked, so the claimed "three latent defects exposed by wiring" cannot be diff-verified; only their absence in the current source is confirmed.
