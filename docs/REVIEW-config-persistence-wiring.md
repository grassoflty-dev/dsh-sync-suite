### Minor
1. **A01–A04 guard the pure helper, not the adapter.** If the old bare `await Promise.all(pending); await store.flush();` returned to `configStore.ets`, A01 would still be green; only A05's source regex (`configPersistence.test.mjs:792`) would catch it, and a regex can be evaded by rewording. `.ets` is outside the Node gate, so adapter-level injected-failure evidence is source-shape only. The fix itself is present and correct, so M1 is closed.
2. **Envelope-helper key coverage is uninstrumented.** W01 pins the 40/3 `legacyKeys` and W09 pins flat-key puts, but no test checks that `settingsEnvelopeBytes` / `extrasEnvelopeBytes` assign every key. Manual inspection confirms 40/40 (`:364-403`) and 3/3 (`:80-82`) today. A future `ScheduleSettings` field added to the spec and `save()` (both guarded) but omitted from the helper would make the envelope stale while flat keys stay correct — the M1 review's m1 half-wire hazard, closed only by convention here.
3. **"Envelope is the truth" is aspirational in the production read path.** `load()` (`settingsStore.ets:500-621`) never decodes the envelope; W05's "new instance reads back from the envelope" is a pure-layer seam simulation. The real app reads flat keys (which are maintained in lockstep), so there is no user-visible bug, but fail-closed and round-trip claims rest on flat keys rather than on the envelope.

## Residual risk & unverified
- **No ArkTS build and no device run.** `services/*.ets` are excluded from `tools/tsconfig.json`; `tsc` covers only `.ts` models. Nothing installed (build 1000005; device check with 1000006). All runtime IO behavior — migration, rollback, fail-closed, write-through — remains `unverified`, and the 1000006 before/after hash comparison has not been done.
- **Restore's byte-exactness has an assumption.** The adapter clears the reserved key on rollback (`configStore.ets:232`) because it is empty before a normal rewrite (true in the real flow and in A01's fixture). An exotic pre-state where `config.schema` itself held a legacy flat JSON would be cleared rather than restored byte-for-byte. When `restore()` itself rejects (A03), only the typed result is guaranteed; physical envelope bytes may be partial, but legacy flat bytes are never touched and the app degrades to legacy reads.
- **Fail-closed "no reset" presumes flat keys exist.** If the envelope is the only data on a device and becomes unknown-version, `load()` returns defaults; that is the inherent cost of never overwriting unknown bytes, not a regression of this module.
- `preferences.getPreferences(...)` in both `init()` methods is outside the try/catch (pre-existing). An adapter failure *there* would still reject startup; only migration failure is guarded.
- W01–W10 are source-shape assertions plus pure-layer simulations; they are not executable ArkTS/IO tests. The owner's one transient A01 red occurred before the adapter fix was in the tree; I saw no failure in any gate run.
