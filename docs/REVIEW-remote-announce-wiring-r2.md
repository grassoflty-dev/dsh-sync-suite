## Residual risk & unverified

- **No device run.** Real ArkTS/SDK behaviour (`createAsyKeyGenerator('Ed25519')`, `convertKeySync`, `verifySync(null, {data})`, `PersistentStorage.persistProp` for both new keys) is evidenced only by a successful `CompileArkTS`; no DevEco install or on-device verification.
- **Q1 host key source still deferred.** `docs/REMOTE-DISCOVERY.md:24` leaves Ed25519 key generation/rotation open; `:13` says the App verifies against the *pinned public key*. On device, `publicKeyFingerprint` must therefore be a raw 64-hex Ed25519 public key and the host must sign with the matching private key. The model accepts 16–64 hex fingerprints (`remoteAnnounce.ts:195`), but `hexToBytes` requires exactly 32 bytes (`remoteAnnounceStore.ets:424-428`), so a genuine short hash fingerprint would still fail signature verification. This is a host-conformance prerequisite (and r1 m3 wording tension), not a code unreachability in this lane.
- **Byte-identity limit.** The zero-write guarantee is proven decision-level via the fake port's JSON snapshot; no executable test hash-compares the real AppStorage keys / instance table on cancellation (Node cannot run `.ets`). The real-store property rests on the early returns at `remoteAnnounceRefresh.ets:174-185` and `model/remoteAnnounceRefresh.ts:174-181`.
- **Two-store non-atomicity (unchanged from r1).** `instanceStore.upsert()` and `remoteAnnounceStore.applyUpdatedAt()` are separate commits (`remoteAnnounceRefresh.ets:123-124`); a lost second write allows idempotent re-application, not an address swap. Both stores swallow their own write errors.
- **Carry-overs not fixed here.** r1 m2 (sticky `announceNotice`, `reload()` at `InstancesPane.ets:159-164` does not clear it) remains; r1 m3 (field-name/contract ambiguity) remains, though `REMOTE-DISCOVERY.md:13` supports the raw-key reading used by the fix. r1 m1 is now user-observable (M2-r2).
