# Review — mod-instances-pairing

## Verdict
CONDITIONAL PASS — the pairing parser, FNV checksum (typo-only), IPv6/fingerprint normalisation, zero-write TOFU refusal, pin preservation across reachability/announcement refresh, single URL builder, configurable-only UI, and compiled-artifact evidence all verify first-hand with no Major defect; the pass is conditioned on two evidentiary gaps (weak pristine-HEAD baseline proof, no retained full-suite gate log for the quoted 3691/3687/3/1 run) and on-device behaviour remaining unverified. Major findings remaining: 0

## Findings

### Blocker
None. The token never reaches a typed error string, a `console.*` call, a toast, or the rendered row; a fingerprint mismatch cannot reach `commit()`; the pin is preserved on every refresh path; there is no second URL builder; the two-step signed-announcement consent flow is byte-for-byte intact in behaviour; and the compile evidence exists and was reproduced independently.

### Major

### Minor
- **M1 — the "would fail on pristine HEAD" proof is weak (check 6).** `apps/arkui-schedule/tools/test/pairingPayload.test.mjs:32-33` performs top-level `await import('../.build/model/pairingPayload.js')`, and `pairingPayload.ts` is a new untracked file. On a pristine HEAD worktree that import raises `ERR_MODULE_NOT_FOUND` before a single test body runs, so all 12 cases fail *for import reasons*, not because the old behaviour differs. The executor's three extra booleans (`pairingText=false`, `已固定指纹=false`, `addByPairing=false`) are static-source observations that could not have executed in that worktree. The claim is credible as a mechanism (the module and UI hooks are indeed new) but proves novelty, not behavioural regression coverage. A stronger baseline would copy the compiled `.build` artefacts into the HEAD worktree (or stub the module) so P1-P6 execute against old logic.
- **M2 — no retained log for the quoted full-suite gate (check 8).** A workspace-wide grep for `3691`, `3687`, and `build-20261122-181058` finds no gate-capture file; `apps/arkui-schedule/.tmp/` holds only `build-rc2.out` (build tail) and unrelated older logs. I cannot verify the 3691/3687/3-fail/1-skip attribution *from a log* as requested. The attribution is nevertheless corroborated: current `git status` shows the concurrent RC-1 plugin lane actively editing `packages/dsh-dots/src/client.js` and `dist/client.js` plus `test/client-lean-*.test.mjs`, and an earlier independent review (`docs/REVIEW-settings-configured-state.md:37`) records exactly the same three plugin dist-freshness failures (`client-loader-id.test.mjs:62`, `client-render.test.mjs:180`, `client-remote-render.test.mjs:479`). None of the three is in this module's files.
- **M3 — pairing "update" recomputes `id` from the new URL, leaving announcement-pin state orphaned.** `apps/arkui-schedule/entry/src/main/ets/model/pairingPayload.ts:546-556` sets `id: id` (derived at `:525` from the new host/port). The requirement asks to preserve name/pin/reachability and one row — all satisfied — but `remoteAnnounceStore` pins are keyed by the old `id`, so a same-instanceId/same-fingerprint address change silently detaches any pre-existing signed-announcement pin. `tools/test/pairingPayload.test.mjs:193-205` (P6-2) does not assert `id` stability. Semantically the two pins are documented as independent (`:18-19`), so this is not a pin overwrite, but it is an untested cross-path edge.
- **M4 — the pin is a payload-consistency check, not a live TLS verification.** `pairingPayload.ts:519` hardcodes `scheme: 'http'` (the plugin's `node:http` listener; comment at `:517-518` says the certificate exists only as a TOFU pin). The WebView path (`InstancesPane.ets:297-308` → `mergeRemoteToken` → `pages/RemoteControl`) opens plain HTTP, so no TLS handshake consumes `tlsFingerprint`. The requirement explicitly scopes the connection to the existing remote WebView path, so this is compliant as specified; it is recorded because "verify TLS fingerprint" could otherwise be read as on-the-wire verification.

### Nit
- **N1 — refusal wording differs from the exact quoted string.** Required: `可能是换了机器或中间人；请先删除旧实例再重新配对`. Implemented (`pairingPayload.ts:98-99`): `该实例的证书指纹与已保存的不同，可能是换了机器或中间人；请先在平板上删除旧实例再重新配对` — an extra `在平板上` sits between `请先` and `删除`. Both consequence regexes in P6-1 pass and the meaning is identical; only a literal-string comparison would flag it.
- **N2 — checksum error copy mentions scanning.** `pairingPayload.ts:377` says `请重新扫描或逐字核对`, but scanning is explicitly out of scope this round (paste only). Harmless, slightly stale instruction.
- **N3 — misleading host reason for `host:port` under `lan`.** `normalisePairingHost` (`pairingPayload.ts:257-261`) treats any colon as IPv6, so `192.168.1.6:44996` under `lan` returns `该传输方式要求 IPv4 或主机名，不能用 IPv6 地址`. The typed code (`E_PAIRING_HOST`) is correct; only the Chinese detail is imprecise.

## Checklist

1. **Parser correctness — PASS.** Both forms accepted (`pairingPayload.ts:458-485`; JSON at `:466-474`, `DSHDOTS1|` at `:475-483`). Exact key set enforced at `:402-411`; only `v:1` at `:412-414`. FNV-1a 32-bit at `:335-343`, verified in `parseCompact` at `:367-394`; the header comment at `:2-19` and `:335` explicitly state it is a typo check, not authentication, and an attacker can trivially recompute it. **Transposed typo caught (verified first-hand):** swapping `AbCd`→`bAcd` in the token of the plugin-generated compact string returns `{ok:false, payload:null, code:'E_PAIRING_MALFORMED', reason:'配对串校验和不对，请重新扫描或逐字核对'}`. Every malformed class maps to its own code (`:397-442`): MALFORMED / VERSION / TRANSPORT / HOST / PORT / TOKEN / FINGERPRINT, plus the TOFU conflict code at `:544`. All reasons are fixed Chinese literals built only by `parseFail`/`normaliseFail`/`addFail` (`:113-126`); no input value is ever interpolated. Test P2 (`pairingPayload.test.mjs:90-115`) and P5 (`:144-164`) pin this; I also read every message string in the file. No token can reach an error or log.

2. **Normalisation — PASS.** `compressIpv6` (`:159-234`) expands `::`, strips leading zeros, compresses the longest zero run (leftmost on ties), and lowercases; `normalisePairingHost` (`:242-301`) brackets IPv6, lowercases scheme-less hosts, rejects schemes/paths/ports; port integer 1-65535 at `:427-430`; fingerprint 64-hex or colon-separated → `AA:BB:…` at `:303-322`. First-hand probes: `2001:0DB8:0000:0000:0000:0000:0000:0001` + `ipv6` → `[2001:db8::1]`; `[::1]` → `[::1]`; `[[::1]]` → `ok:false` / `IPv6 主机格式不合法` → `E_PAIRING_HOST`; `http://192.168.1.6/` → `host 不能带 http:// 或 https://` → `E_PAIRING_HOST`; mixed-case colon fingerprint → canonical uppercase; 63-hex → `E_PAIRING_FINGERPRINT`; ports 0 and 65536 → `E_PAIRING_PORT`; `v:2` → `E_PAIRING_VERSION`. Test P3 (`:117-132`) and P4 (`:134-142`) agree.

3. **TOFU pinning — PASS.** `addPairedInstance` (`:507-591`) matches on `pairingInstanceId` (`:531-537`); existing + different fingerprint returns `addFail('E_PAIRING_FINGERPRINT_MISMATCH', …)` with `items: []` (`:539-545`) — zero rows, zero writes. `InstanceStore.addByPairing` (instanceStore.ets:145-151) calls `commit()` **only** on `result.ok`, so the store layer also performs zero writes on refusal. Refusal copy at `pairingPayload.ts:98-99` names 换了机器或中间人 and 删除旧实例再重新配对 (see N1). Same-id/same-fingerprint updates address/port/token while preserving name, `reachable`, `tlsFingerprint` and `lastSeen` in one row (`:546-568`); first add creates one row with the pin (`:571-590`). **Pin survives every refresh:** `applyReachability` (instances.ts:589-595), `encodeInstances`/`decodeInstances` (instances.ts:434-437, 646-651, 703-712), and the announcement service `storeAddress` (remoteAnnounceRefresh.ets:123-129) all copy `pairingInstanceId`/`tlsFingerprint`. Test P6-1/2/3 (`pairingPayload.test.mjs:170-223`) pass; no pin silently dropped.

4. **One URL builder — PASS.** The only `scheme://host:port` template in the app model tree is `announcementBaseUrl` (`model/remoteAnnounceRefresh.ts:102-105`), widened from `Announcement` to `BaseUrlParts` (`:90-94`, comment `:83-89`). Pairing reuses it at `pairingPayload.ts:519` with `{scheme:'http', host:innerHost, port:payload.port}`, stripping its own brackets first (`:514-516`) so the builder re-adds them; the result is revalidated by `normalizeRemoteUrl` (`:520-523`). Pairing contains no second URL constructor (P7-3 at `pairingPayload.test.mjs:254-258` enforces this; grep of `model/*.ts` confirms). Direct `http://host:port` is produced (P6-1 asserts `http://192.168.1.6:44996` at `:178`, P6-3 asserts `http://[2001:db8::1]:44996` at `:212`). **HTTPS** is expressible only by passing `scheme:'https'` in `BaseUrlParts` (the signed-announcement path at `remoteAnnounceRefresh.ts:146`); pairing deliberately hardcodes `http` because the plugin listener is `node:http` (`:517-518`). **Token destination:** it is stored in the instance envelope's `token` field only (instances.ts:640-642), then merged into the **URL query `?token=<encoded>`** by `mergeRemoteToken` (`remoteUrl.ts:495-514`; `k` is also recognised on read at `:174`, `:319`), passed as `params['url']` to `routeToRemote()` / `pages/RemoteControl` in `InstancesPane.ets:297-308`. No header, no log, no rendered value.
