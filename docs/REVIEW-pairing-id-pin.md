# Review — mod-pairing-id-pin

## Verdict
PASS — preserving `existing.id` on the same-instanceId/same-fingerprint update keeps every id-keyed store (announcement pin, applied time, grants, redaction, instance table) coherent, the add path and the legacy/no-pin refusal are intact, P8-1/P8-4 genuinely fail on the pre-fix code, and the 3042-test app suite plus all build/artifact evidence verify first-hand. Major findings remaining: 0

## Findings

### Blocker
None. The fix removes the only write that changed an instance's id behind the back of every id-keyed store; no row is duplicated, no pin is overwritten, and no error path leaks a token or fingerprint value.

### Major
None. In particular:
- No id-keyed consumer breaks as a result of this change. `remoteAnnounceStore` pins (`remoteAnnounceStore.ets:275-303`), the applied-time table (`:339-361`), the announcement file path (`remoteAnnounceRefresh.ets:79-90`), grant keys (`instanceGrant.ts:327-334`, `455-499`), redaction/sort (`instances.ts:490-533`) and `upsertInstance` (`:515-534`) all read the **stored** `id`, which is now preserved. `remoteAnnounceRefresh.storeAddress` (`remoteAnnounceRefresh.ets:108-132`) already used exactly this policy — `id: instance.id` with a changed URL and the explicit comment 「id 是公告签名的稳定身份，不按新地址重算」 — so `pairingPayload.ts:549` aligns the pairing path with the pre-existing announcement path rather than introducing a new invariant.
- A legacy row without a pin cannot be admitted to the update branch: `pairingPayload.ts:541-545` computes `storedKey` from `existing.tlsFingerprint` (undefined/empty ⇒ `''`) and refuses with `E_PAIRING_FINGERPRINT_MISMATCH` when `storedKey.length === 0` or `storedKey !== incomingKey`. `incomingKey` is never empty because the parser requires a 64-hex fingerprint (`:435-437`, `:530`). This is at least as strict as the announcement TLS rule 「没有 pin ⇒ 只允许带显式首配标志的路径」 (`remoteAnnounce.ts:457-466`).
- The tests would **not** pass on pre-fix code: P8-1 fails at `row.id === oldId` (pre-fix id = hash of the *new* URL, so the pin seam at the old id returns `''`) and P8-4 fails its `id: existing.id` / no-`id: id` assertions. P8-2 and P8-3 are regression guards that pass both before and after.

### Minor
- **M1 — absent-fingerprint case is code-correct but untested.** `pairingPayload.test.mjs` P6-1/`:170-191` and P8-3/`:332-345` cover *different* fingerprints; no case covers a row with `pairingInstanceId` but a missing or empty `tlsFingerprint`. The refusal is present at `pairingPayload.ts:541-545`, but if that `storedKey.length === 0` guard were later relaxed, no test would catch the silent upgrade. Add a P8-5 asserting `E_PAIRING_FINGERPRINT_MISMATCH` and zero writes for such a row.
- **M2 — a later manual form save can still re-key a paired row (out of scope, not a regression).** `InstancesPane.ets:365-398` recomputes `id = instanceIdFromUrl(check.url)` and, under 「改地址 = 换 id」, removes the old row and upserts a new one when `id !== this.formId` (`:394-398`). After this fix a paired row's stored id intentionally lags its updated URL, so saving that row from the form (even only to rename it) recreates it under the new URL-derived id and orphans the announcement pin again. This policy predates the mod and already applies to announcement-refreshed rows (`remoteAnnounceRefresh.ets:108-132`), so it cannot be attributed to `mod-pairing-id-pin`; it does mean the guarantee is scoped to the pairing path, not to every edit path. Flagged for follow-up, not fixed here.

### Nit
- **N1 — the `capabilities` half of the fix has no runtime effect.** `deriveCapabilities(_id)` ignores its argument entirely (`instances.ts:327-336`: 「保留 `_id` 形参只为兼容既有调用点，能力集不再按 id 分叉」), so `deriveCapabilities(existing.id)` at `pairingPayload.ts:555` is byte-for-byte the same value as the old `deriveCapabilities(id)`. Consequently P8-1's `assert.deepEqual(row.capabilities, I.deriveCapabilities(oldId))` (test `:309`) and P8-4's capabilities source-shape assertion (`:354-355`) are cosmetic; the behaviourally discriminating assertions are `row.id === oldId` and the pin lookup. Harmless, and consistent with the add path at `:580`.
- **N2 — P8-4 is a literal source guard** (test `:347-360`): a harmless reformat of the object literal could trip it. This is intentional given the requirement that a revert to `id: id` must fail the suite.

## Checklist

1. **The fix is the right one — PASS (residual M2).** `git diff` confirms only two source lines changed plus the explanatory comment: `pairingPayload.ts:549` `id: existing.id` (was `id: id`) and `:555` `capabilities: deriveCapabilities(existing.id)` (was `deriveCapabilities(id)`). Grep of all `getPin(`/`setPin(`/`instanceIdFromUrl(`/`deriveCapabilities(` call sites shows every id-keyed consumer uses the stored `id`: `remoteAnnounceRefresh.ets:69,110,131,141,159,185,195`; `remoteAnnounceStore.ets:275-303,339-361`; `instanceGrant.ts:327-334,455-499`; `instances.ts:331-336,490-534`. `decodeInstances` → `normalizeInstance` (`instances.ts:384-442`) validates only the `inst-<16hex>` shape and does **not** recompute the id from the URL, so a row whose id no longer equals `hash(url)` survives persistence. No consumer that breaks was found; the manual-form re-key path (M2) is a pre-existing, separate policy.

2. **Add vs update are still distinct — PASS.** `:525` `const id: string = instanceIdFromUrl(check.url);` is untouched — verified in the read-only `git diff` (no hunk above `@@ -544`) and asserted by P8-4 (test `:358-359`, which inspects `model.slice(0, updateAt)`). The update branch is selected solely by `pairingInstanceId` equality at `:531-539`; a genuinely new `instanceId` falls through to `created` at `:573-583` with `id: id` and `capabilities: deriveCapabilities(id)`. P8-2 (test `:317-330`) does more than compare two ids: it asserts `action === 'added'`, `items.length === 2`, the new row's `pairingInstanceId === 'new-pc'`, `added.id === I.instanceIdFromUrl('http://192.168.1.9:45002')`, and `added.id !== first.items[0].id`. This proves the two paths are distinct.

3. **No silent upgrade path — PASS (coverage gap M1).** The lookup at `:532-537` requires `items[i].pairingInstanceId === payload.instanceId`. A legacy row carrying `pairingInstanceId` but no `tlsFingerprint` therefore reaches the update branch, where `:541-545` sets `storedKey = ''` and returns `addFail('E_PAIRING_FINGERPRINT_MISMATCH', PAIRING_FINGERPRINT_MISMATCH_WORDING)` with `items: []` before any field is written. A legacy row with neither field cannot match at all and follows the add path. The zero-write discipline is enforced again at the store layer (`instanceStore.ets:145-151`: `commit()` only when `result.ok`). Consistent with the announce module's 「no pin ⇒ refuse unless explicit first pairing」 rule (`remoteAnnounce.ts:457-466`).

4. **Tests are real — PASS.** Targeted run: `node --test apps/arkui-schedule/tools/test/pairingPayload.test.mjs` → `tests 16 / pass 16 / fail 0`, exit 0. P8-1 (test `:292-315`) sets a pin keyed by `oldId`, updates host/port/token, then asserts `pins.getPin(row.id) === announceKey` — i.e. the pin **resolves after** the update, not merely that two ids are equal — plus `items.length === 1`, updated `url` and `token`, unchanged `tlsFingerprint`, and `action === 'updated'`. P8-4 (`:347-360`) slices the literal update branch and requires `id: existing.id`, forbids `id: id` and any `instanceIdFromUrl(` in it, and requires the URL-derived `const id:` in the pre-branch text; reverting `:549` to `id: id` fails it. The pin "seam" (test `:279-290`) is an in-memory replica of `setPin`/`getPin`; I compared it against `remoteAnnounceStore.ets:275-303` and the keying/`hasOwnProperty` semantics match.
