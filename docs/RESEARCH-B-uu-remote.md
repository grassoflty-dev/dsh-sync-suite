## 0. 结论（一句话判定 + 3 条依据）

**判定：网易 UU 远程（及其同系的 GameViewer 远程）不能当隧道用——它是「远程桌面 / 画面串流」，官方功能集里根本没有端口转发、内网穿透、虚拟局域网；平板端拿到的是「设备 ID + 验证码 → 进入桌面」，不是可被 App 内嵌 WebView 打开的 URL。**

依据：

1. **官网功能清单里没有任何端口/映射/组网条目**。`https://uuyc.163.com/` 的「特色功能」全量导航为：文件传输、高清画面、隐私防护、多屏协作、远程开机（WOL）、按键映射、Mac 电脑被控、无线副屏；使用场景为远程办公 / 远程游戏 / 远程协助 / 客厅畅玩。没有一个属于网络层能力。
2. **帮助中心全量目录里也没有**。`https://uuyc.163.com/help/` 的「功能指引」（电脑控电脑、手机控电脑、远控 Mac、远程协助、文件传输…）与 `https://uuyc.163.com/help/questions/` 的「常见问题」（12 条：手柄、键鼠、灵敏度、宏按键、错误码、虚拟摇杆…）逐条核对，**无端口映射 / 内网穿透 / 异地组网 / 虚拟 IP 任何一项**。
3. **连接模型是账号/ID 而非地址**。官方文档明确：手机端需与被控端「均登录就绪」，从设备列表点「进入桌面」发起远控（[手机如何通过网易UU远程控制电脑](https://uuyc.163.com/help/20241203/40220_1197649.html)）；远程协助是「被控端复制设备 ID 和验证码 → 协助方输入」（[远程协助](https://uuyc.163.com/features/support/)）。**被控端仅支持 Windows / macOS**（同页原文：「其他系统暂不支持远程被控」）。整个链路不存在「把 127.0.0.1:PORT 发布成一个 URL」的概念。

## 3. 为什么远控类产品不能当隧道（技术说明）

1. **转发语义不同**。远控链路传输的是「编码后的屏幕帧 + 输入事件」（H.264/HEVC/自研编解码 + 鼠标坐标、键盘扫描码、手柄/触控事件），中间经过信令服务器与媒体中继；**没有一个环节在转发 IP 包或 TCP 字节流**。所以它对端到端 TCP 握手、HTTP/1.1 或 WebSocket 升级、Keep-Alive、大包分片等一无所知。
2. **没有虚拟网卡 / 没有路由**。隧道（WireGuard、Tailscale、frp 的 tun 模式、蒲公英二层组网）会给设备分配虚拟 IP 并改路由表，让平板"看起来"和家里 PC 同一网段。远控类不分配虚拟 IP、不接管路由，平板端没有任何可 dial 的地址（不存在 `100.x.y.z:40596` 这种东西）。
3. **没有 URL 出口**。远控产品对外的寻址键是「设备 ID / 账号关系 + 验证码」，服务端不提供「把本机某个端口发布成 `https://xxx`」的接口；客户端 App 也不会把解码画面交给 WebView。我们的 App 需要的是「内嵌 Web 打开一个 URL」，远控给的是「一台远程 Windows 桌面」。
4. **壳内再开浏览器 ≠ 隧道**。理论上可以「远控进家里 PC → 在远程桌面里打开浏览器访问 127.0.0.1:40596」。这确实能看到界面，但：① 变成"操作整台 PC"，不是 App 原生 Web 壳；② 延迟/丢帧/输入法/剪贴板/文件拖拽全部受串流质量影响；③ 平板要装远控 App 并保活；④ 被控端只能是 Windows/macOS 且必须客户端在线（关机后仅靠 WOL，需主板+网卡支持）。对「平板随时打开 DSH Web GUI」这个目标，它是**降级方案**，不是本任务要的隧道。
5. **所以**：凡「本质是远程桌面/画面串流」的产品（UU 远程、GameViewer、ToDesk 个人版、向日葵基础远控、Parsec 等），**一律不能复用为端口隧道**；判定不依赖会员等级或平台细节。

**表内小结论**

- 「零自建 + 平板只当客户端 + 直接得到可内嵌的 URL」这一组合，国产方案里目前只有**花生壳**是原生形态（HTTP→HTTPS 域名映射，浏览器即可打开，无需平板装客户端）。
- **蒲公英**是国产里最接近 Tailscale 的形态（虚拟局域网、P2P 优先、全平台客户端），代价是平板必须常驻客户端 + 登录 + 带宽档位付费。
- **向日葵/ToDesk/UU 远程**这类远控，哪怕新增了「内网穿透」营销词（向日葵），其主形态仍是远控客户端；要做隧道必须确认具体套餐与客户端形态（未取到，需人工确认）。
- 三者都**不需要自建服务器**（用厂商云中转），因此不与"不采用自建服务器方案"的决策冲突；真正的取舍是「把内网流量交给第三方厂商中转 + 实名/付费带宽限制」vs「Tailscale/Cloudflare 的国外控制面」。

## 5. 推荐替代与排序

给定约束（不自建服务器、平板访问家里 DSH Web GUI、App 内嵌 Web 打开 URL），推荐排序：

1. **Tailscale（WireGuard mesh，首选）** — 零自建、免费档够用、端到端加密、平板装 App 后能拿到 `100.x.y.z` 直连家里 PC，DSH 只需额外监听该接口（或本机反代）。P2P 打洞成功时延迟最低；被墙/打洞失败时会走 DERP 中继（国内体验需实测）。
2. **Cloudflare Tunnel（次选，纯 URL 形态最省事）** — 家里 PC 跑 `cloudflared` 出站连接即可，得到 `https://xxx.trycloudflare.com` / 自有域名的固定 HTTPS URL，**平板零客户端、纯浏览器/WebView 直接打开**，最贴合"App 内嵌 Web"。代价：需要 Cloudflare 账号与域名（named tunnel），国内访问速度和稳定性需实测。
3. **公网 IPv6 直连（最省资源，条件最硬）** — 家宽有公网 IPv6、平板所在网络（4G/5G 或外部 Wi-Fi）也支持 IPv6 时，直接 `https://[2408:...]:PORT`；零第三方、零费用、延迟最优。代价：两端 IPv6 都要通、防火墙/前缀变动、地址难记。
4. **兜底：花生壳（要 URL 就它）/ 蒲公英（要虚拟局域网就它）** — 当上面三条在国内网络环境下不可用时，用国产云中转替代，同样不需要自建服务器。花生壳给 HTTPS 域名（平板免客户端），蒲公英给虚拟 IP（平板需客户端）；两者都要实名并受带宽档位限制。

一句话：**先试 Tailscale（体验最好）→ 只要"一个能嵌的 URL"就选 Cloudflare Tunnel → 有 IPv6 就 IPv6 直连 → 都不行再用花生壳/蒲公英兜底。UU 远程这条线直接划掉。**

> 与前序决策的衔接（重要）：DSH 默认只听 `127.0.0.1`。上述任一方案落地时都需要二选一：① 让 DSH 额外 bind 到隧道接口地址（如 `100.x` / 局域网口）；② 由隧道客户端把远端请求反代到 `127.0.0.1:40596`。**UU 远程两种都做不到**——它不产生接口，也不产生反代。
