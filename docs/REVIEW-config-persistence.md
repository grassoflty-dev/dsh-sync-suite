# Review — mod-config-persistence

## Verdict
CONDITIONAL PASS — the pure schema/rewrite logic, both invariant scans, all gates and the doc rows are sound and honestly scoped, but the preferences adapter can let an async write/flush failure escape to its caller despite a documented "never throw to UI" guarantee, and the write-through obligation that must prevent a future stale-config half-wire is documentation-only. Major findings remaining: 1

While this review was running (file mtimes 12:27:57 / 12:28:24 on 2026-11-22), a **separate `mod-config-persistence-wiring` change landed** in `services/settingsStore.ets` and `services/syncController.ets` — see the addendum at the end. Findings below describe the module as commissioned; the addendum records how the concurrent change alters checks 6/9/10 and escalates M1 from latent to live. ## Findings

### Blocker
None. None of the four automatic-FAIL triggers fired: an unknown version cannot overwrite bytes (`refuse`, zero writes, original bytes unchanged — `configSchema.ts:230-237`, `configSchema.ts:184-192`; tests F01/F02), the rewrite is observably idempotent (test M03), the legacy chain cannot resurrect stale config (a found `ok` current envelope stops the chain and yields `no-write` — `configSchema.ts:257-259`), and no row claims a build that did not happen (§10).

### Major
**M1 — `configStore.migrateOnce()` does not contain the final put/flush awaits, so an IO failure can reject the public method and reach the UI (`apps/arkui-schedule/entry/src/main/ets/services/configStore.ets:218-221`).**
`runWithSeam` correctly converts a *synchronous* `seam.write` throw into a typed `storage-unavailable` refuse (`configSchema.ts:297-307`, test F03). But the adapter's seam `write` only *pushes* promises (`configStore.ets:213-215`); the actual `await Promise.all(pending); await store.flush();` at `:219-220` sits outside any `try/catch`. A rejected `preferences.put()` or `flush()` therefore propagates out of `migrateOnce()` as an unhandled rejection. This directly contradicts the file header's claim that "所有公开方法都吞掉异常、只返回 typed 结果，不把异常抛进 UI" (`configStore.ets:8-9`). Tests do not cover this path: F03 only exercises the pure layer's synchronous throw seam, and S01 merely asserts the *text* `if (outcome.wrote)` (`configPersistence.test.mjs:360`), which gives false assurance that "IO exceptions → typed, no throw to UI" holds at the service layer. At review time this was latent only because the module was not wired; the concurrent `mod-config-persistence-wiring` change now calls `await configStore.migrateOnce(...)` unguarded inside `SettingsStore.init()` and `GitExtrasStore.init()`, so M1 is **live on the startup path** in the final tree (see addendum). Fix by wrapping the write/flush block in `try/catch` that returns a typed `refuse` with `wrote:false`, and add an adapter-level test with a rejecting `put`/`flush`.

### Minor
**m1 — Write-through obligation is documented but unenforced; "cannot silently half-wire" is true only of the current tree.** The header (`configStore.ets:14-16`) correctly states that after the one-time rewrite the `{v:1,values}` envelope is authoritative and later saves must update it. But no test or type enforces this: a future wiring that writes the envelope once and keeps saving legacy flat keys would silently serve stale values on the next launch (the chain finds the envelope first — `configStore.ets:115-118`), and no guard would catch it. The claim is TRUE for HEAD (no importers, no hardcoded store names, S01 text guard) but is not a structural guarantee.

**m2 — A non-numeric `v` key is reinterpreted as ordinary legacy data and gets overwritten.** `decodeEnvelope` only treats `v` as a version marker when `typeof v === 'number' && Number.isFinite(v)` (`configSchema.ts:130-142`); `{v:"7", token:"x"}` falls through to the legacy flat-table path (`:143-149`) and `migrateOnce` will rewrite over it. That is a latent fail-open if any future writer emits a string/other non-numeric version marker. All current envelopes use numeric `v`, and E04/E05 do not cover this case.

**m3 — A `{}` current slot stops the legacy chain instead of falling through.** `decodeEnvelope('{}')` returns `legacy` with an empty value map (not `empty`), so `resolveLegacyChain` returns `found` and `migrateOnce` yields `no-write/legacy-empty` (`configSchema.ts:261-263`; test M05 at `configPersistence.test.mjs:221-234`). A legacy store behind it would not be consulted. Harmless in the real adapter because `collectCandidates` never emits a candidate for a store with no values (`configStore.ets:120-129`), but the pure-layer semantics differ from "empty values are skipped".

**m4 — The stated reason for the deliberate stop is stale.** Docs say `settingsStore.ets` is "正由 `mod-ai-models-fetch` 修改" / "须等其提交" (`MODULES.md:111,207,328`; `ROADMAP.md:484`), yet the same docs record that module as already committed at `bf19548` (`MODULES.md:109`), which is the actual HEAD. The non-wiring itself is real, but the "another uncommitted module owns those files" justification no longer holds; Lead must re-authorize wiring explicitly rather than treat the gate as still closed.

### Nit
**n1 — HEAD mismatch with the brief.** The brief states HEAD `8e4a20c`; `git rev-parse HEAD` returns `bf19548` (`mod-ai-models-fetch`), one commit ahead. Review used the real working tree; scope checks were run against both `HEAD` and `8e4a20c`.

**n2 — M04 proves semantic equality, not literal byte equality.** Extra-key preservation is asserted via `deepEqual(decoded.values, legacy)` (`configPersistence.test.mjs:216-218`); canonical byte determinism is proved separately by M03's exact string comparison (`:201`). Together adequate, but "byte-for-byte" is only indirectly covered.

**n3 — I01 is a line-based scan.** A rawfile path passed to a write API split across lines would evade the `write\w*\([^)]*rawfile` regex (`configPersistence.test.mjs:320-321`). Current anchors are genuine (see §5), so the guard is not vacuous, but it is not a data-flow proof.

**n4 — Stale pre-existing line in the same doc.** `PERSISTENCE.md:82` still says "本轮只读：不改 `apps/**`、不改测试、不构建、不写 git；唯一写入是本文档". It was not touched by this module's purely-additive diff, but it now contradicts the new section and the added app/test files.

**n5 — §2 scope row omits the exact unverified boilerplate.** `MODULES.md:207` says only "`.ets` 未编译 / 未装机 `unverified`" without the full 「未装机 / unverified（安装版 `1000005`；设备检查随 `1000006`）」 string; §1 (`:111`), §5 (`:328`) and `ROADMAP.md:484` carry it. This matches the precedent of other modules' §2 rows, so not a regression.

## Residual risk & unverified
- **No ArkTS build and no device run.** `configStore.ets` is not compiled (tsconfig excludes `services/`), nothing is installed, and no real preferences/PersistentStorage I/O was exercised. All runtime behavior — including the adapter path in M1 — is `unverified` (installed build 1000005; device check with 1000006).
- **M1 is now live in the final tree.** The concurrent wiring change calls `configStore.migrateOnce()` unguarded in both `init()` methods (startup path) without first fixing the adapter; an IO failure there will reject into app startup. Fix the adapter before shipping any 1000006 install and add a rejecting-`put`/`flush` test.
- **Write-through is a convention only.** After wiring, nothing stops a save path from continuing to write legacy flat keys; the envelope would go stale on next launch. Needs a guard (or a single accessor owning all config writes).
- **Baseline hashes are facts, not proof.** The three 1000005 hashes are recorded verbatim but the 1000006 before/after comparison has not been performed; any difference must be reported as a fact, not a failure.
- **Wiring authorization is stale.** The brief and docs assume `mod-ai-models-fetch` is uncommitted; it is committed at `bf19548` (HEAD), so the stated blocker for wiring is gone. Lead must re-approve wiring explicitly.
- Minor latent edges m2 (non-numeric `v`) and m3 (`{}` chain stop) are untested but unreachable in the current real adapter flow.

## Addendum — concurrent `mod-config-persistence-wiring` change (not in the commissioned scope)
While this review was being written, a separate change (self-labelled `mod-config-persistence-wiring`) modified two files owned by other modules:

- `services/settingsStore.ets`: imports `CONFIG_ENVELOPE_KEY`, `encodeEnvelope`, `createConfigStore`; exports `SETTINGS_CONFIG_SPEC` (39 legacy keys, `legacyNames: []`); adds `settingsEnvelopeBytes()`; `envelopeWritable` flag; `init()` now does `const outcome = await configStore.migrateOnce(abilityContext)` **with no try/catch**; write-through envelope puts in both save paths, gated by `envelopeWritable`. `aiModelsCache` is deliberately excluded from the envelope.
- `services/syncController.ets`: analogous `GIT_EXTRAS_CONFIG_SPEC` (3 keys), `extrasEnvelopeBytes()`, `envelopeWritable`, unguarded `await configStore.migrateOnce(...)` in `init()`, and a write-through put in `GitExtrasStore.save()` (its enclosing catch still covers disk errors there).

Consequences: (a) check 6's "nothing imports `configStore` yet" is false in the final tree — the module was honest as delivered, but the stop has since been reversed by another module; (b) check 9's AI-file boundary is now crossed by that other module, not by `mod-config-persistence`; (c) check 10's "未接线" rows are stale until docs are updated; (d) M1 ceases to be latent: both `init()` methods now await the unguarded adapter directly, so a put/flush rejection reaches startup. Also note the write-through paths hand-build the envelope from a fixed field list — future added settings fields must be added to both `legacyKeys` and `settingsEnvelopeBytes()` or they will be silently omitted from the envelope while still being saved as flat keys (the exact half-wire hazard m1 warns about). This addendum is an observation, not a review of the wiring module; that module needs its own independent review and gate run.
