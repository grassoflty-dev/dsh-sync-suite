# Review — mod-home-list-instant-refresh

## Findings

### Blocker

### Major
None.

### Minor
1. **Every return to `Home` now performs a full reload, even with no save.** With the pane's `onPageShow()` live in the shell route, a return with a null marker takes the `reload() + loadSummary() + paneTick++` branch (`SchedulePane.ets:387-390`, previously unreachable there). This is an idempotent `timelineStore.readDay` re-read, not a correctness bug, and no harmful double-fire exists: the wide-shell save path (`onEditorSaved`, `SchedulePane.ets:684-694`) consumes the marker itself and does not navigate, so no `Home.onPageShow()` tick occurs for that save. The only overlap is a later, separate return (e.g. from Settings), which re-reads once more harmlessly. Confirm on device that repeated returns do not produce visible flicker.
2. **`paneTick++` in the no-marker branch is unconditional.** If a user opens Settings from the rail while a right-pane editor is dirty and then returns, `paneTick` advances (`SchedulePane.ets:389`); the dirty-edit guard exists only in the pull-to-refresh handler (`:1791-1796`). Inspection of `RecordEditorView.onRefreshTick()` (`RecordEditorView.ets:262-265`) shows it only applies pending ink results, not a full re-read, so the draft is not obviously destroyed — but this edge case should be exercised on device.
3. **"Home is the only `@Entry`" is imprecise wording.** The repo has multiple `@Entry` pages (`Index`, `Edit`, `Detail`, `Settings*`, etc.). The correct, verifiable statement is that `Home` is the shell-route `@Entry` hosting `SchedulePane` (`Home.ets:72-74, 212-216`) with `Index` as the registered fallback (SG-S5, `structureGuards.test.mjs:378-386`). The mechanism is unaffected.

### Nit
1. `HLR-04/05/06/08` (and P-27/L-25's tail assertions) are source-shape pins that would also pass on the old code; only `HLR-01/02/03` plus the new P-27/L-25/SG-S4 lines actually fail on the old tree. This is acceptable — the suite as a whole fails on old code — but the "root cause" is proven by static shape, not by executing the trigger chain (which cannot run in Node).
2. `HLR-06` pins `Index`'s chain statically only; it cannot prove the fallback's `onPageShow` fires on a real page. Code inspection confirms `Index.ets:136-137` is `@Entry` with `onPageShow` at `:318-345`, so the claim stands.
