# Review — mod-home-startup-sync

## Verdict
PASS — The cold-start path provably claims its one-shot quota synchronously before the first `await`, routes the single cycle through `globalRefreshCoordinator.runOnce()`, keeps both blocker gates authoritative, and every compile/artifact number was independently reproduced; no Major finding remains. Major findings remaining: 0

## Findings

### Blocker
None.

### Major
None. Specifically: no two-cycle race, no coordinator bypass, no cycle before readiness, no cycle from an unconfigured/denied state, and no fabricated compile evidence — see Checklist 1–3 and 8.

### Minor
1. **Home.ets runtime wiring is only statically pinned.** HSS-01..05 are behavioural, but they exercise a spy rig over the pure model plus the *real* coordinator and predicate, not the ArkUI page. The ETS side (`GitBridgeHost` → `ensureStarted` → `isReady()` → coordinator → `syncStatusStore` failure line) is verified only by string assertions in HSS-06/HSS-07 (`homeStartupSync.test.mjs:253-323`). A future edit that preserves the literals but rewires a call target (e.g. `onReady` to a no-op, or `reportFailure` to a toast) would not be caught at runtime. This is inherent to "ArkUI cannot run in Node", but it is a real residual risk, not a proof of runtime correctness.
2. **The cited `tsc` artifact is absent.** `MODULES.md:376` and `ROADMAP.md:769` cite `.tmp/tsc-home-startup.out` for `tsc` exit 0; no such file exists in the tree at review time. The three gate artifacts that do exist were read and match their claims (Checklist 9). This is an evidence-formality gap only — it does not hide a failing gate.

### Nit
1. **Docs row coverage is uneven and line numbers are unstable.** MODULES.md §1 (`:156`), §5 (`:376`) and ROADMAP.md (`:769`) cite `build-20261122-154124.log` inline and carry the exact status string 「已写完（待 Lead 提交，状态 / 哈希（Lead 填））」. The §2 file/scope row (currently `:239`) has no build-log citation because that table has no evidence column. MODULES.md grew from 490 to 496 lines during this review (sibling lanes committing concurrently), so every line number here is a snapshot.
2. **"One cycle per cold start" is implemented as "one cycle per process".** `requested` (`homeStartupSync.ts:52,84-88`) is never reset, so a later `onPageShow` after backgrounding/navigation will not start another cycle. Desirable for the 「无感同步」 requirement, but the phrase should not be read as "one per foreground".

## Residual risk & unverified
- **On-device cold launch is unverified** (installed `1000007`; 1000008 pending). No force-stop → launch → `git_sync_status` advancing / repo `HEAD` leaving unborn was reproduced here. Compile success, source shape and spy tests are proxies for the exact symptom this module closes.
- **ETS wiring is static-only** (Minor 1): string assertions cannot prove the runtime call graph or the failure-line target.
- `isRepoConfigured` and `guardPush` live in sibling lanes; the behavioural tests consume the compiled `.build/model/repoConfigured.js`. A source change in that lane without a fresh `tsc` could stale those tests.
- Process-singleton semantics (Nit 2), and the theoretical case of `GitBridgeHost` emitting neither `onPageEnd` nor `onErrorReceive`, would leave a deferred request unsatisfied with no status write (the component does emit one of them in practice).
- Docs line numbers shift under concurrent commits; all citations are snapshots taken during this review.
