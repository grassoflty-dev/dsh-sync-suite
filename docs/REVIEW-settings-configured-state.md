# Review — mod-settings-configured-state

## Verdict

FAIL — The real-device symptom (a valid configured repo shown as 「未配置 · 未同步」) is fixed and the cycle/privacy ordering is sound, but a predicate‑configured repo with a hostless URL can still render 「未配置」, and the migration / save→cold‑read tests are source‑shape plus in‑memory re‑decoding rather than behavioral; Major findings remaining: 2

## Findings

### Blocker

None.

### Major

1. **A predicate-configured repo can still print 「未配置」.** `repoHostOf()` returns the literal `'未配置'` whenever the URL parses to an empty host (`model/settingsMenu.ts:13–21`). `repoRowSummary()` accepts that string as `head` because it only tests `head.length > 0` (`model/repoConfigured.ts:100–104`), while `repoConfigStateOf()` declares the same input configured as long as `repoUrl` and `token` are non‑empty (`model/repoConfigured.ts:56–67`). Example: `repoUrl='https://'` (non‑empty, hostless) + any token ⇒ `configured=true`, `repoHostOf()='未配置'`, summary `未配置 · 未同步` — exactly the reported defect string. In the blocked branch the same input yields `未配置 · 已配置（可见性阻断，禁止推送）`, i.e. both labels at once (`pages/Settings.ets:77–81`). Low probability on saved data (`validateRepoUrl` rejects it), but reachable from migrated/imported preferences. Fix: treat `host === '未配置'` as an empty host in `repoRowSummary` (fall back to `'仓库'`).
2. **C2 and C5 do not prove what they claim.** `configuredState.test.mjs:43–58` (C2, "envelope-only migration") and `:91–108` (C5, "save→cold read") never call `settingsStore.load()` against a preferences seam with the flat keys absent/emptied. They encode and immediately re‑decode an envelope in memory, feed a hand‑built object to the pure predicate, and assert source regexes (`/decodeEnvelope\(rawEnvelope\)/`, `/prefs\.put\(CONFIG_ENVELOPE_KEY, …\)/`). `configPersistence.test.mjs` covers `decodeEnvelope`/`migrateOnce` at the pure layer, but no test exercises the new fallback branch at `services/settingsStore.ets:518–535`. The code is correct by inspection; the migration claim is unproven by tests. C5's "privacy refusal never clears" assertion (`:107`) is likewise a regex on `pages/SettingsSync.ets:312–316`, not a save/load roundtrip.

### Minor

1. **Diagnosis is directionally right but over-attributed.** Confirmed by code: pre‑fix `Settings.ets` initial value was `'未配置 · 未同步'` (diff `@@ -46,7 +50,8 @@`) and is replaced only after async `bootstrap()`; this alone explains the mislabel. The other three cited facts do **not** explain the mislabel: `settingsStore.load()` reads prefs directly rather than `this.cache` (`services/settingsStore.ets:500–643`), so `cache = null` is irrelevant to the UI summary; `GitSyncService.config = { repoUrl: '', … }` (`services/GitSyncService.ets:626–633`) feeds the legacy service, not the wired cycle; and Home at HEAD has no `ensureStarted()` call but does call `runConfiguredCycle()` — that explains "no cycle ever ran", not the wrong label. The new config guard refuses an unconfigured cycle but does not itself make a configured repo sync on the real entry path (a concurrent, out‑of‑scope lane is editing `Home.ets` for that).
2. **Full-suite gate is red/unstable on this moving tree.** Observed across four runs: 3585/3584/0/1, 3586/3583/2/1, 3592/3588/3/1, plus one run with two `EADDRNOTAVAIL` failures. None is owned by mod-settings-configured-state.

### Nit

1. `setConfigReader()` is public on the singleton and `runCycle(ctx)` remains a public entry with no config guard; production has no caller of either today (`grep` finds only the definitions and the internal `runConfiguredCycle → runCycle(ctx)` hop). A future direct `runCycle` caller would bypass the new check.
2. `repoConfigured.ts:48–50` treats `authMode==='ssh'` as needing no token, but `repoVisibilityChecker.guardPush():98–102` returns `allowed=true` when the URL yields no HTTPS target and the wired `GitPort` path has no explicit SSH block (the SSH refusal lives only in legacy `GitSyncService.ets:2476`). Such a repo is "configured" and may reach the wired cycle; it will still fail at transport, so this is a semantic, not a push-safety, gap.

### M1 closure — CONFIRMED
- `model/repoConfigured.ts:143–163`: `repoRowSummary` checks `!state.configured` first (`:149`), then `hostText.length === 0 || hostText === REPO_HOST_PLACEHOLDER` (`:155`) and returns the single label `未配置：仓库地址格式不正确` (`:156`) **before** the blocked branch (`:159`). A hostless **and** blocked repo therefore returns the format-error label only — never `未配置 · 已配置（可见性阻断，禁止推送）`; C8 asserts this directly (`configuredState.test.mjs:186–188`), along with `no '未配置 · '` (`:185`).

- **Nit:** the replacement label still begins with 「未配置」 while `state.configured === true`. It is no longer the reported defect string and it names the real problem, but the label/predicate wording remains semantically inconsistent.

### M2 closure — CONFIRMED
- The seam is genuinely the production path: `services/settingsStore.ets:526–540` calls `readRepoConfigFromPrefs(...)` **unconditionally** (no flag, no early return) with a real-prefs adapter — `getFlat` serves the flat `prefs.get` values read at `:523–525` (`:527–535`), and `getEnvelope` always performs `prefs.get(CONFIG_ENVELOPE_KEY, '')` (`:536–539`). `load()` therefore cannot silently skip the envelope fallback; there is no surviving duplicate merge (`decodeEnvelope` is no longer imported in `settingsStore.ets:48` and appears in production only at `repoConfigured.ts:14,86`).
- Tests invoke the same exported function on the compiled module (`configuredState.test.mjs:25,61,81,125,130,138`), not a test-only copy. C2 now behaviorally proves all-flat-absent + envelope ⇒ url/token returned, configured, `repoCycleGuard().start === true`, `writes === 0`. C5 proves flat+envelope after save, envelope-only cold read, and corrupt envelope + no flat ⇒ unconfigured + named field + `writes === 0`. The seam has no write method (`repoConfigured.ts:53–58`); the tests add a `put` counter as an extra guard.
- **Nit:** the production adapter's `getFlat` defaults any unknown key to `flatAuthValue` (`settingsStore.ets:528`). Correct for the three keys currently read, but `REPO_KEY_AUTH_MODE` is never compared explicitly, so a future key addition would silently receive the auth-mode value.
