## New findings

### Blocker
None. No path force-pushes, rebases, hard-resets remote history, or touches `devices/**` (`test.mjs:405-443`; `git-bridge.js:2182` keeps `force: false` ×2 in HAP).

### Major
1. **M3b's writer contract is not implemented in production — the fix is inert for a genuinely missing schema.** The premise in `syncCycle.ts:457-458` and in both docs (`docs/MODULES.md` §2 row, `docs/ROADMAP.md:671`) says the writer's `writeDay` goes through `timelineWriteStore.requireSchema()` → `ensureSkeleton()` to create the marker. `timelineWriteStore.ets` has **no** `writeDay` method; its `requireSchema()` (`:283-289`) and `ensureSkeleton()` (`:116-125`) exist, but the production `WritePort` is built in `syncProtocolStore.ets:319-327` with `writeDay → this.writeDayTexts(date,texts)` (`:320-322`), and `writeDayTexts` (`:334-361`) only calls `atomicReplaceText`/`appendDedupLines` — it never calls `requireSchema()`, `ensureSkeleton()`, or any schema write. Consequently, if `timeline/schema.json` were actually absent at bootstrap time, stage 1 would not create it, the re-read at `syncCycle.ts:532-547` would still see `''`, and the code would refuse with `E_SCHEMA_UNKNOWN` before `addPaths`/`commit` — the same fail-closed outcome as before the M3b fix. Virgin installs work only because an unrelated startup path pre-creates the marker: `Index.ets:387-398` (`bootstrap()` → `summaryStore.ensureReady` at `:394`) → `summaryStore.ets:32-40` (`:38`) → `timelineWriteStore.ets:96-105` (`:104` → `ensureSkeleton()` at `:116-125`), also reachable from `SchedulePane.ets:431`. The post-stage-1 re-read is therefore **real guard logic in the pure model (test 22 proves it), not dead code**, but it cannot make the production allow-missing path succeed. Acceptance evidence is correspondingly weak: test 19 (`test.mjs:584-599`) passes only because the *fake* writer (`writeOf`, `test.mjs:228-243`, lines 233-235) creates the schema itself. Fix: either make `syncProtocolStore.writeDayTexts` guarantee the marker (call `timelineWriteStore.requireSchema()`/an explicit skeleton-ensure before day writes), or state honestly that schema is guaranteed by startup `ensureReady` and treat missing-at-bootstrap as a genuine fail-closed error; correct the source comment `syncCycle.ts:457-458` and both doc statements either way. Severity Major, not Blocker: fail-closed, no history/data risk, and the standard startup path masks it.

### Minor
1. **Bridge-not-ready error is now misclassified on the production port.** `requireService()` throws `E_SYNC_UNAVAILABLE` (`gitRunner.ets:57-58`; constant at `syncCycle.ts:174,180-181`). Because production `remoteLayout()` calls `requireService()` first (`gitRunner.ets:139`), that rejection is now swallowed by the probe catch (`syncCycle.ts:610-616`) and `typedProbeCode` (`:409-416`) maps the unknown `E_SYNC_UNAVAILABLE` prefix to `E_GIT`. The special case in `runWiredCycle` (`syncProtocolStore.ets:284-288`) therefore no longer fires for `BridgeGitRunner`; the user sees `E_GIT: 远端状态探测失败（E_SYNC_UNAVAILABLE: …）` instead of the intended `unavailableOutcome` (`syncCycle.ts:238-240`). This is a second normal-path behavioural delta beyond the documented `E_PULL_FAILED`, and no test pins it. Still typed and retryable, so Minor.
2. **Stale line citations in the docs.** `docs/MODULES.md` §5 row and `docs/ROADMAP.md:671` cite `syncCycle.ts:511-517` for the `E_PULL_FAILED` fetch catch; after the M3b insertion the actual code is `syncCycle.ts:626-632`. The M3b citations `syncCycle.ts:456-482` / `:530-547` are also off by a few lines (actual pre-write gate `:462-482`, post-write re-read `:532-547`). The `bootstrapSchemaGate` citation `:361-371` should be `:361-369`. Content is right; only the anchors drifted.
3. **M1's tags-only pinning is model-level, not bridge-level.** Test 12 (`test.mjs:461-473`) injects `{hasMain:false,isEmpty:false,refs:['v1']}`; it proves the `no-main` branch but would not catch a regression in the bridge's all-ref-category enumeration. The bridge expression is only pinned statically (`test.mjs:436-437`) because bridge JS cannot execute in the node harness. Residual, not a defect.
